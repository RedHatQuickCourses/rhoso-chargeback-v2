In this unit, we will prepare your Red Hat OpenStack Services on OpenShift environment, or RHOSO, for chargeback. We will achieve this by installing the necessary dependencies and enabling the Rating service, also known as CloudKitty. You will use provided Ansible playbooks to automate these tasks, building upon the concepts covered in our previous theory modules regarding prerequisites and enabling the Rating service.

First, let's connect to your workstation machine. All lab tasks must be performed from here. If you haven't done so already, please install the `ansible-core` package by running `sudo dnf install ansible-core`. You will run all subsequent commands from this terminal.

Next, you need to clone the training repository, which contains all the automation scripts for this lab. Execute a `git clone` for the `rhoso-chargeback` repository and then navigate into that directory.

This repository is organized into four directories, each containing an Ansible playbook for a specific stage of the lab. The `pre-deploy` directory handles the installation of Loki, MinIO, and the Cluster Observability Operator. The `deploy` directory updates your OpenStack control plane to enable Telemetry, Ceilometer, MetricStorage, and CloudKitty. The `create-ck-rating` directory automates the creation of a hashmap rating rule, and finally, the `validation` directory ensures that your configuration was applied correctly.

Now, let's install the CloudKitty dependencies. As we discussed in the theory modules, CloudKitty requires a Loki instance for storing data, backed by S3-compatible storage, along with the Cluster Observability Operator to manage MetricStorage. To set this up, run the playbook located at `pre-deploy/deploy-ck-dependencies.yml`.

This playbook is quite comprehensive. It waits for the OpenShift Route API to become available, then applies several Kubernetes manifests. These manifests create the `openshift-operators-redhat` and `minio-dev` namespaces, set up subscriptions for the Loki and Cluster Observability operators, deploy a MinIO pod with 10 gigabytes of persistent storage, and finally, create a secret named `cloudkitty-loki-s3` in the `openstack` namespace to hold your MinIO credentials. The playbook concludes by waiting up to five minutes for the operators to reach a succeeded status.

A quick note: this playbook expects to find files relative to the repository root. If you are running the command from a different location, ensure you override the path by passing the `ansible_user_dir` variable to your command.

With the dependencies in place, we can move on to enabling the Rating service itself. This involves modifying the `OpenStackControlPlane` custom resource. Run the deploy playbook by executing `ansible-playbook deploy/update-deployment-for-ck.yml`.

This process performs several critical actions. It adds the `CloudKittyPassword` to your `osp-secret`, then systematically activates the Telemetry, Ceilometer, MetricStorage, and CloudKitty services within the control plane. It will then wait for the `OpenStackControlPlane` to transition to a ready state. Please keep in mind that this step is significant and may take up to 30 minutes to complete while the operator reconciles all changes. It is very important that you do not interrupt the playbook during this time.

Once the playbook finishes, it is time to verify your deployment. You should confirm that the `cloudkitty-api` and `cloudkitty-processor` pods are in a running state by using the command `oc get pods -n openstack` filtered by `cloudkitty`. Next, confirm that the CloudKitty custom resource reports a ready condition using `oc get -n openstack CloudKitty`. Finally, ensure that Ceilometer and MetricStorage are also fully ready by checking their status with the `oc get` command for each resource in the `openstack` namespace.

Once all components report that they are ready, your environment is fully prepared for rating. You are now ready to move on to the next unit, where you will create your first rating rule.
