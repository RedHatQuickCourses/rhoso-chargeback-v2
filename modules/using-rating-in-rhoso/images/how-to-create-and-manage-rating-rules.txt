In this session, we will explore how to create and manage rating rules. These rules are applied automatically to your resources through the use of mappings, which tell the system exactly when and where a specific cost rule should be implemented.

There are two primary ways to configure these rules, depending on the level of granularity you require. The first method is Field Mapping. This is used when you want to adjust the rating based on a specific characteristic or configuration value of a resource. For example, you could charge different rates for storage depending on the `volume_type` field, such as applying one rate for High-Speed SSD and a lower rate for Standard HDD. Similarly, you could map the `flavor` or `instance_type` field to charge different hourly rates for different instance sizes.

The second method is Service Mapping. This is best when you want to link a rate directly to an entire service or usage metric, regardless of its specific configuration. For example, you might assign a flat rate to a metric like `ceilometer_ip_floating` to charge for allocated public IP addresses, or associate a flat fee per one thousand operations for a storage metric.

To create a rating rule, you will follow a six-step process: creating a hashmap group, retrieving the collected metrics, creating a hashmap service, optionally creating a field matching rule, creating the hashmap mapping, and optionally setting thresholds.

Let’s walk through these steps in detail.

First, you must create a hashmap group. A group allows you to separate different sets of mapping calculations so they remain independent. For instance, you might want to keep your virtual machine uptime rules separate from your block storage rules. Use the command `oc exec openstackclient -n openstack -- openstack rating hashmap group create` followed by your desired group name. Please note that the group name does not need to match the metric name collected in Prometheus.

Second, retrieve the metrics collected by the rating service by running: `oc exec openstackclient -n openstack -- openstack rating info config get -f yaml`. This provides the data you need for subsequent steps.

Third, create a hashmap service to link your rules to specific metrics. Run the command `oc exec openstackclient -n openstack -- openstack rating hashmap service create` followed by the metric name. A critical warning here: the metric name you provide must match the `alt_name` associated with the metric. If no `alt_name` is defined, it must match the metric name exactly. Verify this by checking the configuration data you retrieved in the previous step.

Fourth, you may optionally create a field matching rule if you need to refine the rating based on metadata. Use the command `oc exec openstackclient -n openstack -- openstack rating hashmap field create` providing the service ID and the field name. You can use any metadata attribute or group-by property defined in your metric configuration as a field.

Fifth, create the hashmap mapping. This is the object that triggers the actual cost calculation. Use the `openstack rating hashmap mapping create` command. You will specify the cost, the service ID, the group ID, and the mapping type. The map type can be set to `flat`, which adds a cost to the total, or `rate`, which multiplies the total cost by the rate. If you are using field-specific values, ensure you have retrieved the correct field ID using the `field list` command first.

Finally, you can optionally create thresholds to apply rating rules only after reaching a specific usage level. These work similarly to mappings and can be tied to a specific project. Use the `openstack rating hashmap threshold create` command, specifying the threshold level, such as a specific number of compute hours, alongside the rate and service identifiers.

By following these steps, you can precisely control how resources are rated and billed within your environment.
