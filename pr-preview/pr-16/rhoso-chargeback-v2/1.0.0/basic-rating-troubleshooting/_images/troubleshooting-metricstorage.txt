In this module, we will focus on troubleshooting MetricStorage. 

MetricStorage is responsible for managing the Prometheus instance that stores all of your collected metrics. It is a critical component; if MetricStorage is not running correctly, metrics will not be available to the Rating service or to Ceilometer scrape targets, effectively breaking your entire metric pipeline.

Let’s begin by looking at how to handle a situation where MetricStorage is not running correctly.

This issue occurs when the MetricStorage Custom Resource exists, but its status conditions indicate a problem, which in turn prevents Prometheus from deploying. To diagnose this, first verify the status by running the command `oc get metricstorage`. Ideally, you should see the status set to true with the message "Setup complete." If the message is different, it will often provide a hint regarding the issue. 

For more granular detail, you can inspect the status conditions using a JSON path query with the `oc get metricstorage metric-storage` command, piped through `jq`. When reviewing the output, look specifically for any conditions where the status is set to false. The `message` and `reason` fields here are your best resources for diagnostics. For instance, if you see an error indicating that a monitoring stack resource is not found, this is a strong indicator that the Cluster Observability Operator has not been installed.

To resolve these issues, always read the condition messages carefully, as they often point directly to the solution. If the problem relates to missing operators, network attachments, or TLS configurations, address that specific component mentioned in the status output.

Now, let’s move to a common scenario: MetricStorage is not enabled. 

If MetricStorage has not been deployed, it is likely because it is not enabled within the control plane Custom Resource. Without it, there is no Prometheus instance to store your data. To diagnose this, you can check your telemetry and MetricStorage configuration settings by running the `oc get oscp` command with the appropriate JSON path queries for both the telemetry and metric storage enabled flags. Both should return "true." If either value is "false," simply edit the control plane Custom Resource to set both of these values to "true" to restore functionality.

Finally, let's discuss the Cluster Observability Operator, or COO. 

MetricStorage relies on the Cluster Observability Operator to manage MonitoringStack resources. If this operator is missing, MetricStorage cannot function, and its status conditions will explicitly report that it cannot own the MonitoringStack resource. 

To confirm this, check the MetricStorage status conditions as we discussed previously. If the reason field indicates that the Cluster Observability Operator is likely not installed, you will need to install it. You can do this by creating a Subscription Custom Resource. The command uses the `oc create` directive with a provided configuration block to set up the operator in the `openshift-operators` namespace. Once the subscription is created, the operator will be installed automatically, and MetricStorage should reconcile itself until it reaches the "Setup complete" state.

By following these diagnostic steps and checking your resource statuses, you can quickly identify and resolve the most common issues affecting MetricStorage within your environment.
