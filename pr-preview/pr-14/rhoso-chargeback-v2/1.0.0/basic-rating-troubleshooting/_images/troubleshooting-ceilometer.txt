In this training, we will cover how to troubleshoot Ceilometer, a key component of the OpenStack Rating service. Ceilometer collects usage data from your OpenStack resources and exposes them as Prometheus metrics. If it isn't deployed correctly, fails to expose metrics, or if Prometheus cannot scrape them, the Rating service will lack the data it needs to function.

### Troubleshooting Ceilometer Deployment

If metric collection isn't starting, the first step is to verify that Ceilometer is enabled and ready on both the control plane and the data plane.

To diagnose this, you can check the OpenStack control plane configuration using the `oc get oscp` command to confirm that both telemetry and the Ceilometer sub-component are set to true. Next, verify that the Telemetry and Ceilometer Custom Resources are deployed by running `oc get telemetry` and `oc get ceilometer`. You should see that the status is "True" and the message confirms "Setup complete." If you don't see this confirmation, the status message will often provide specific guidance on how to fix the issue.

Finally, check the data plane deployment by inspecting the `openstack-edpm-ipam` resource. You are looking for a status of "True" and a message confirming that the deployment is ready for the telemetry service.

If you find that Ceilometer is not enabled, you will need to edit the control plane CR and update those fields. If the CR exists but is not ready, always read the message and reason fields for troubleshooting clues. If it’s missing from the data plane, verify that the telemetry service is included in your nodeset service list.

### Troubleshooting Metric Exposure

Sometimes Ceilometer is running, but its agents are failing to serve metrics at their endpoints. This means Prometheus has nothing to scrape.

To diagnose this, you can use `curl` from the `openstackclient` pod to query the Ceilometer central agent at port 3000. You should see `ceilometer_` metric lines in the output. Similarly, you can query a compute node’s agent at port 9101—replacing the IP address with your specific compute node—to see compute-related metrics like CPU usage or disk read bytes.

If these endpoints return no data despite having active resources, this often indicates a software bug. Always double-check that you are using the correct ports: 3000 for the central agent and 9101 for the compute agents.

### Troubleshooting Scrape Failures

Even if Ceilometer is exposing metrics, Prometheus might still be unable to see them. This usually points to a misconfiguration in the scrape settings or a network connectivity issue.

Start by verifying the scrape configuration for `telemetry-ceilometer` and the compute-specific scrape configuration `telemetry-ceilometer-compute-prom-exporter-tls`. Ensure that the scheme matches your TLS settings and that the targets are correctly listed.

To see if Prometheus is successfully reaching these targets, run the `openstack metric show up` command. You are looking for a value of 1 for the relevant Ceilometer jobs. If you see a 0, the target is down. In that case, use the Prometheus targets API to query the status—the output will include a `lastError` field, which is critical for identifying exactly why the scrape is failing.

When resolving these issues, remember:
*   If your scheme is wrong, such as using HTTP when TLS is required, update the configuration.
*   If you have a connection timeout, check your network and firewall rules between the Prometheus pod and the Ceilometer endpoints.
*   If you see a TLS error, verify that your certificates are valid and match the ones used by your agents.

By following these diagnostic steps, you can methodically isolate whether your issue stems from deployment, metric exposure, or the Prometheus scrape configuration.
