Rating rules assign value to the consumption of computing resources within your environment. While a set of metrics is exposed to the CloudKitty rating service by default, you can define specific metrics for your deployment by using a custom metrics.yaml configuration file. 

In this training, we will walk through the process of defining these collected metrics. The procedure consists of eight key steps: copying the default file, identifying available metrics, defining the collection logic, performing optional unit conversions or multi-aspect rating, creating a Kubernetes secret for your configuration, updating your control plane, and finally verifying the implementation.

To begin, retrieve the default metrics.yaml file from the cloudkitty-proc pod. You can copy it to your local machine for editing by running the oc exec command to cat the file from the pod into a local file named metrics.yaml.

Next, you need to know which metrics are available for configuration. You can view the list of metrics currently being collected in your RHOSO deployment by running the oc exec command against the openstackclient pod, using the openstack metric list command.

Once you have your configuration file and list of metrics, you can define how each metric is collected. Within the metrics.yaml file, you will specify the metric name and various attributes. These attributes include the unit of measurement, grouping parameters, metadata, and optional unit conversion factors or offsets. You can also specify mutation operations, such as rounding or mapping values, and provide extra arguments to control how data is retrieved from Prometheus. For instance, you might use an aggregation method like max, or define a query function like ceil or floor. 

The configuration also supports mapping values; for example, you can map specific power status codes to a binary value, such as setting a running instance to one and a shutdown instance to zero.

If your data requires unit conversion, such as moving from bytes to megabytes, you can define a factor and an offset. The system calculates the final quantity using the formula: quantity equals collected quantity multiplied by the factor, plus the offset. Additionally, if you need to rate different aspects of the same resource, you can define multiple units for a single metric. By adding distinct rating blocks under one metric name, you can track different attributes, such as both the resource flavor and CPU time, simultaneously.

After you have finalized your custom metrics.yaml file, you must create a secret to store it within OpenShift. Use the oc create secret generic command to generate a secret named cloudkitty_secret using your local file. You can verify the creation by describing the new secret.

The final integration step involves updating your OpenStackControlPlane custom resource. Use the oc edit command to modify the resource, and add your secret name to the cloudkittyAPI and cloudkittyProc sections under the telemetry template. 

A critical warning here: Always back up your custom resource definition before making any modifications. Incorrect configuration can disrupt your telemetry services and impact the stability of your environment.

Once you save the changes, the Telemetry Operator will automatically detect them and initiate a reconciliation process. Monitor your cloudkitty pods to ensure they restart and adopt the new configuration. To complete the process, verify the changes by running an oc exec command to cat the metrics.yaml file directly from the cloudkitty-proc pod, ensuring it matches your custom configuration.
