In this session, we will explore the architectural overview of Red Hat OpenStack Services on OpenShift, or RHOSO. Specifically, we will focus on its observability components. Having a solid grasp of this architecture is essential for effectively managing, monitoring, and troubleshooting your RHOSO environment.

The RHOSO observability architecture uses a hybrid approach. It combines established OpenShift tooling with native OpenStack telemetry solutions to ensure robust metric collection and logging across the entire technology stack.

When we look at the core components, we start with those that are native to OpenShift. RHOSO utilizes four key services in this area:

First, there is the Cluster Observability Operator, or COO. This is an optional component of the OpenShift Container Platform that allows you to create and manage highly customizable monitoring stacks. 

Second, we have the Cluster Logging Operator, or CLO. This operator provides a set of APIs to control the collection and forwarding of logs from all pods and nodes in your cluster. It handles three distinct types of logs: application logs from your regular pods, infrastructure logs from system pods and nodes, and finally, audit logs, which are specific node logs that carry legal and security implications.

Third, the OpenShift Console UI provides a single, unified graphical interface where you can visualize your metrics, logs, alerts, and dashboards.

Fourth, the Telemetry Operator acts as a vital bridge. It integrates OpenStack-specific telemetry data into the OpenShift ecosystem, ensuring that metrics and logs from your OpenStack services are correctly collected and exposed to your OpenShift monitoring tools.

While RHOSO leverages these OpenShift strengths, it also retains two key OpenStack-native telemetry solutions that will be familiar to OpenStack administrators:

Ceilometer is the primary data collection service. It provides the ability to normalize and transform data across all core OpenStack components and continues to be the primary gatherer of OpenStack-specific metrics.

Complementing Ceilometer is AODH, the OpenStack Alarming service. AODH allows you to define specific rules based on the metric or event data collected by Ceilometer, which can then trigger automated actions.

Regarding how these services are deployed, they operate across two different layers of your infrastructure. Services like the Cluster Observability Operator, the Cluster Logging Operator, and the Telemetry Operator run directly within your Red Hat OpenShift Container Platform cluster to manage the overarching observability framework. Simultaneously, services running on your OpenStack Dataplane nodes provide node-specific metrics and logs, ensuring you have full coverage across your entire data plane.
