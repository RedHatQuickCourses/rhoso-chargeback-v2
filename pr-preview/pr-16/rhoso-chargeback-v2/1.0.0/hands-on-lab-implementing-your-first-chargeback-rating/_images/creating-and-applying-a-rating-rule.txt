In this unit, we will walk through the process of creating a hashmap rating rule. By the end of this exercise, you will have configured a rule that assigns a specific cost to compute instances based on their flavor. We will be using the `openstack rating` CLI commands within your Red Hat OpenStack Services environment.

Before we begin, let’s quickly recap a few core concepts. The rating module defines how CloudKitty processes and applies your rules; the `hashmap` module is the recommended approach because it uses metric metadata to create rules. Rules are organized into groups, which are logical containers. A service connects your rule to a specific metric—keep in mind that the service name must match the metric’s `alt_name`. You can optionally define a field to target specific metadata, such as a flavor ID. Finally, a mapping associates a cost with your service or field, using either a flat, fixed charge or a percentage-based rate.

Now, let's move to the hands-on activity. You will be creating a hashmap rule that applies a flat cost of zero-point-three to instances using the `m1.tiny` flavor.

Please note that all `openstack rating` commands must be executed through the `openstackclient` pod running in the `openstack` namespace.

First, enable the hashmap module. You cannot create any rating rules until this module is active. Run the command: `oc exec -n openstack openstackclient -- openstack rating module enable hashmap`.

Second, create a rating group. We will name this group `instance_uptime_flavor_id` to keep our rules organized. Execute the command: `oc exec -n openstack openstackclient -- openstack rating hashmap group create instance_uptime_flavor_id`. Be sure to copy and save the Group ID from the output, as you will need it later.

Third, create a service matching rule. This connects your rating rule to the instance metric collected by CloudKitty. Use the command: `oc exec -n openstack openstackclient -- openstack rating hashmap service create instance`. Note the resulting Service ID.

Fourth, create a field matching rule. By creating a field named `flavor_id` under your new service, you can target specific instance flavors. Run: `oc exec -n openstack openstackclient -- openstack rating hashmap field create` followed by your Service ID and then `flavor_id`. Save the resulting Field ID.

Fifth, look up the flavor ID. We need the specific UUID for the `m1.tiny` flavor to associate it with a cost. Run: `oc exec -n openstack openstackclient -- openstack flavor show m1.tiny`. Look for the ID field in the output and note it down.

Finally, create the mapping. This step ties everything together by assigning a cost of zero-point-three to your target flavor. Use the `openstack rating hashmap mapping create` command, providing the cost, the Field ID, the flavor UUID, the Group ID, and specify the type as `flat`.

Once this mapping is created, your rule is live. CloudKitty will automatically apply it to incoming consumption data as it processes metrics.

To verify your configuration, you can list active modules using `openstack rating module list`. When checking your rated data, it is a good practice to restrict the query to the current day to prevent timeouts in your lab environment. You can use the `openstack rating summary get` command with specific begin and end date flags. If you don't see data immediately, wait a few minutes, as CloudKitty processes metrics on a periodic cycle.

If you would prefer to use automation, or if you need to reset your environment, the repository includes Ansible playbooks to handle these steps for you. You can run the `cleanup-ck-rating.yml` playbook to start over, or `create-ck-rating.yml` to set up the rules automatically. You can even pass variables, such as `flavor_name` or `rating_cost`, directly to the playbook to customize the configuration for different scenarios.
